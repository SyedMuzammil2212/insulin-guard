# Data pipeline

The Airflow DAG runs daily or manually with retries. Its single task runs `pipeline.py`, which obtains a PostgreSQL advisory lock, reads a repeatable-read snapshot, extracts changed rows using an inclusive `updated_at` checkpoint, writes raw Parquet batches to MinIO, checks identifiers, duplicates, users, units, quantities and timestamps, quarantines rejected rows with reasons, normalizes mmol/L to mg/dL, computes daily/weekly aggregates and seven-day coverage, validates aggregate keys and counts, and atomically replaces curated tables and advances checkpoints. The original database records are not silently deleted when rejected. Names, email and free-text notes are excluded from lake batches; pseudonymous user IDs and health data remain sensitive.

Checkpoints are updated only with a successful curated load. Full snapshot rebuilds incorporate changed, deleted and late-arriving source events into aggregate tables. They do not scale indefinitely. A retry after a lake write may leave an extra batch object; consumers should deduplicate by record ID and update timestamp. Quarantine and raw objects are not transactionally coupled to the database; failed runs can leave orphan objects. Pipeline run status, duration and counts are stored in `pipeline_run_history`; rejected counts are stored in `data_quality_results`. The API reports the most recent run and success. Pipeline failures are reflected in Airflow task state and retried.

The Spark function in `transformation/spark.py` is a standalone example for validated records, not part of the DAG. DuckDB and Pandera are installed for extension but not integrated; the running validation is explicit Python/Pandas code. Airflow currently has one pipeline task, not ten independently observable tasks. No automatic lake retention or account-erasure mechanism exists. Run with synthetic data only.
